# App Generation

## Purpose

将用户的一句话需求转化为可继续开发的完整应用，提供可观察、可恢复的生成进度，并以实际功能和构建结果验证交付质量，减少用户自行理解工具和手工修复代码的负担。

## ADDED Requirements

### Requirement: 一句话启动完整工程生成
系统 SHALL 接收一句自然语言需求，自动形成页面、数据、设计及验收计划，生成源码并执行验证；用户不需要手动选择工具或依次触发阶段。

#### Scenario: 创建预约应用
- **WHEN** 用户提交“做一个宠物美容预约网站，有服务介绍、预约表单、后台查看预约”
- **THEN** 系统生成包含上述页面和持久化预约数据的工程，并展示实际验证结果及预览入口

### Requirement: 真实模型及能力状态
系统 MUST 在缺少有效模型配置时明确提示配置问题，不将模板或占位内容标记为已完成用户需求。

#### Scenario: 未配置模型
- **WHEN** 用户在模型未配置时开始生成
- **THEN** 系统显示可操作的配置提示，不报告“生成成功”

### Requirement: 任务进度恢复与取消
系统 SHALL 展示阶段、正在处理的文件和错误信息，刷新或重新连接后恢复进度，支持取消和从失败阶段重试。

#### Scenario: 断线恢复
- **WHEN** 用户在生成中刷新工作台
- **THEN** 系统显示同一个任务的历史及实时进度，不重复创建生成任务

#### Scenario: 取消后重试
- **WHEN** 用户取消任务后选择重试
- **THEN** 系统保留已有文件并从指定阶段继续，取消前不再启动后续写入任务

### Requirement: 验证通过后才交付
系统 MUST 在依赖安装、生产构建和服务健康检查通过后才报告工程可用，且核心用户流程必须有验证证据。

#### Scenario: 页面可打开但表单失败
- **WHEN** 应用页面返回成功但核心表单无法保存数据
- **THEN** 该应用不得被报告为验收完成，系统提供失败证据及修复入口

### Requirement: 生成设计一致性
系统 SHALL 根据应用类型形成一致的字体、配色、间距及组件规则，并在全部生成页面应用这些规则。

#### Scenario: 多页面一致
- **WHEN** 用户生成包含列表、详情和后台的应用
- **THEN** 各页面使用相同导航、字体及交互规则，主要按钮执行对应操作

### Requirement: 无产品级 token 配额
系统 SHALL 不因固定产品 token 配额截断已授权任务，并支持用户取消与明确错误终止。

#### Scenario: 长任务
- **WHEN** 复杂任务需要多次模型调用
- **THEN** 系统按阶段继续执行并记录实际用量，模型上下文、接口限流或超时错误对用户可见
