用户日志表明依赖安装已在 1m54.8s 完成，类型检查也通过，停留在开发预览检查。此时不在生产构建，也未执行业务验收。代码会启动临时 dev 服务、检查健康接口和真实 HTML、停止该服务，再交给 runner 启动稳定预览。因此本来就有两次服务启动/编译成本；本次保持现有隔离测试数据与回滚行为，不改变该生命周期。

针对同一线上项目 p_mwhj1gw21l9sdn，健康接口和任务接口均未在 8 秒内返回，首次任务查询 15 秒超时。没有 SSH 会话及服务器 CPU/内存数据，不能断言本次线上卡顿的唯一原因，也未在线上执行重启或改配置。

本地已复现并修复：

1. runCommand 的 timeout/abort 仅发停止信号，若子进程/后代持有 stdio 而没有 close，Promise 会一直等待。现强制停止后一秒仍无 close 则结束工具等待并返回 terminationUnconfirmed，保留失败/取消标志；不声称已确认杀死全部进程。
2. 首页响应头、健康请求依赖传输层遵守 AbortSignal。现使用独立硬截止时间，响应头忽略取消也可结束。
3. 健康接口原本等待 body.cancel()；取消操作不结束也会阻塞。现启动取消而不等待。
4. 临时服务输出原本只有退出才可见。现节流推送输出，按启动、健康、首页和清理分步记录，每十秒显示当前等待和耗时。关闭未确认的警告不会被成功 HTML 检查掩盖。

验证日志保存在本地 /tmp/atoms-preview-*.log。新增回归先在旧行为下失败，再在修复后通过。真实受控 Next dev 测试夹具启动加首次编译约 5070ms，随后实际首页 HTML 检查约 145ms；子路径 HTML/JavaScript/API、真实浏览器计数交互和 HMR 均通过。这是本机受控夹具结果，不代表线上服务器耗时；首次编译随服务器负载和应用大小变化。
