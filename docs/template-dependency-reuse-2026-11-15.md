# 模板依赖统一复用

同一模板、Node/ABI/libc、系统架构、执行后端、镜像、pnpm 版本与 registry 下，只需冷安装一次。新项目的依赖准备命中缓存后恢复锁文件与 node_modules，跳过下载与原生编译，继续现有开发预览。Next 首次访问仍会编译页面，运行进程的内存也不会共享。

## 如何生效

部署本次平台代码并按现有方式构建、重启平台即可。默认开启，无需修改生成项目或配置软链接。第一次匹配 next-base 的新项目负责准备缓存，之后项目复用。重启平台后缓存仍可用，同一平台进程的并发请求会共用一次预热；不同平台进程可能分别冷安装，但只原子发布完整结果。

- 缓存默认位于 `data/.template-cache/template-v1-{hash}`，可用 `TEMPLATE_CACHE_ROOT` 指定。
- `TEMPLATE_DEPENDENCY_REUSE=false` 可关闭模板预热复用，保留独立安装和原有成功指纹复用。
- 业务变量不传给模板预热。生成的代码、数据库、上传、运行日志和 `.next` 仍按项目独立。
- 仅忽略 package.json 的 name/version/description；其余字段严格比较。额外包、脚本、自定义 npmrc/pnpm hook/workspace 配置或不同锁文件走独立安装。
- 显式加包时切换独立依赖树，避免 pnpm add 使用已经回收的模板 staging store。

## 为何使用写时复制

恢复使用 `COPYFILE_FICLONE`，支持时复用文件系统数据块，但每个项目拥有独立 inode。修改依赖时自动分离，删除全局缓存不影响已恢复项目。跨项目可写硬链接、直接指向外部的 node_modules 软链接都未启用，也没有放宽路径校验。

CoW 的实际节省取决于服务器磁盘和挂载：XFS 需要启用 reflink，Btrfs/APFS 也需满足各自条件；跨文件系统或不支持时 Node 会回退普通复制。建议把 `TEMPLATE_CACHE_ROOT` 和 `WORKSPACE_ROOT` 放在同一支持 CoW 的文件系统。

`du` 可能把 reflink 共享块重复计入各目录；目录逻辑大小不会变成几 MB。应结合文件系统工具和整个卷的可用空间变化评估，不能累加各项目 du 数值作为物理占用。

## 隔离、故障与清理

预热和恢复 staging 都是平台创建的独立临时项目 `data/projects/atoms_template_*`，不挂载在用户应用可写目录中。安装仍通过 runCommand 和原有 bwrap/Docker 隔离。预热只使用可信模板清单，完成后回收临时项目及其 pnpm 下载仓库，避免每个项目长期保留一份预热 store。SQLite node-gyp 留下的 Python 编译工具绝对链接会在受控 staging 中移除，原生 `.node` 运行产物保留。

缓存清单记录完整文件内容、相对链接、目录/文件权限与锁文件摘要。删包、篡改内容和执行权限损坏都会使缓存失效；失效目录先隔离清理，再重建原子发布。缓存复制错误可回退独立安装；冷安装自身失败或超时保留实际错误，不再自动启动第二轮相同安装。取消一个等待项目不会取消其他项目所有者的预热。

本次没有自动迁移或删除线上旧项目。已有依赖成功指纹仍直接复用，旧候选与项目 pnpm-store 沿用之前的回收机制。统一缓存暂不自动按容量淘汰；环境升级会新增独立缓存。暂停依赖任务后可维护清理旧缓存，已恢复应用不依赖它。进程强制崩溃可能留下 atoms_template_* 临时目录，应在确认没有安装任务运行后清理；正常结束、失败和取消均自动回收。

另外使用本机已经安装的 27 个真实模块组成受控样例（不是公网冷安装测量）：第二项目缓存恢复约 6～7 秒；复制后的 TypeScript CLI、better-sqlite3 原生查询、Next 开发服务子路径 HTML/API、Chrome 按钮交互均通过，未产生生产 BUILD_ID。修改一个项目、删除统一缓存后另一个仍可运行。此结果证明模块迁移与预览可用，不代表线上性能或线上磁盘已启用 reflink。线上部署与首次 pnpm 冷安装仍需在目标服务器验收。
