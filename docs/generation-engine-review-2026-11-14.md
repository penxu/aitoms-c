# 应用生成引擎审查（2026-11-14）

## 范围与证据

检查当前磁盘上的 SPEC/PLAN/BUILD/VERIFY、修复器、模型输出清理、文件/命令工具、进程管理、续聊与预览链路，并对照真实生成工程与历史失败记录。此次不修改生成引擎代码、不运行新的模型生成、不覆盖旧工程。

现有 134 项单测、类型检查通过。另用纯函数输入和内存桩验证了现有测试未覆盖的问题。历史任务混有人工续跑、测试工程、环境故障，不将其汇总为模型生成成功率。

## 第一优先级：会破坏代码、任务或运行状态

### 1. 自动归一与输出清理会破坏合法代码（已复现）

- `app/src/lib/generation/ui-contracts.ts:87` 对整个文件中的 variant 做替换，而非仅处理模板 Button 的属性。输入 `export const product = { variant: "premium" };` 输出变成 variant: "default"，可以通过类型检查但业务含义变了。
- `app/src/lib/generation/next16-routes.ts` 按变量名 params 替换。输入普通同步 GET 函数里的 `const params = { id: "123" }; ... params.id`，输出在同步函数中插入 `(await params).id`，制造新编译错误。
- `app/src/lib/generation/model-output.ts:18` 从整个字符串中提取最长代码围栏。合法 TS 模板字符串若包含 Markdown 示例，函数会丢弃外层文件，只留下示例代码。

建议：结构化文件输出；只移除包裹整个响应的外层围栏；代码转换用 TypeScript AST 限制语法位置和导入绑定，转换后做语法与语义检查。增加“不应修改”的业务枚举、局部 params、字符串/注释等负例。

### 2. 进程管理缺少同项目启动互斥与重启恢复（前者内存复现，后者源码路径确认）

`runner.ts:112` 在 await 分配端口前检查运行 Map，之后才注册。两次并发启动同一项目会创建两个进程，后一个覆盖注册记录，停止时只终止后一个。

平台重启时 cleanupOrphans 只清理失效 PID；仍存活的 detached 子进程保留在数据库，但未恢复到 Map。stopService 只终止 Map 内进程，随后清空数据库记录，因而可能报停止成功但实际服务仍活着。

建议：项目级启动 Promise/互斥；数据库持久化进程身份、启动时间和工作目录；停止前核对身份并支持恢复后的进程，避免 PID 复用误杀。

### 3. 续跑只有阶段级，没有文件级检查点或源码事务（源码确认）

`pipeline.ts:96` 恢复阶段，`stages/build.ts:137` 每次从计划第一项开始生成；create 项即使已有文件，也不传入其当前内容（build.ts:83）。中断后重试会覆盖成功文件，计划版本与磁盘半成品可能混在一起。一次单文件 rename 原子写入无法保证整个工程一致。

建议：run 固定需求/计划/源代码版本；记录每个文件的输入哈希、输出哈希与完成状态；只续跑未完成或依赖变化的文件；在候选工程生成和验证后再切换预览，保留最近可用版本。

### 4. 对话修改、生成、预览没有统一工程写锁（缺少互斥已确认，具体损坏取决于并发）

chat route 仅在提示词中描述当前任务，没有限制与 generation 同时使用写入/命令工具。VERIFY 在 verify.ts:166 删除整个 .next，运行中的开发服务仍使用该目录。多标签页、API 请求、用户点击运行都可能绕过单个页面的 locked 状态。

建议：服务端统一管理项目变更锁，覆盖 chat、BUILD、VERIFY、启动/重启；生产构建放到独立快照或独立产物目录，避免清理正在提供预览的目录。

### 5. 生成模型调用仍可能无限等待（源码确认）

此前新增的等待上限只接到 chat。SPEC、PLAN、BUILD、REPAIR 仍只传 abortSignal，没有总时限、首块时限或无输出时限。连接建立后上游不结束时，任务仍可能长期 running；只靠请求 maxDuration 不能充当自定义 Node 服务器内后台 job 的看门狗。

建议：各生成阶段接入明确等待策略、持久化心跳和最后进展时间；明确区分排队、模型响应、命令执行、已失联；恢复时校验 job 所有者。

## 第二优先级：成功率与完成度

### 6. 自动修复无法补缺文件，且无效修改仍重复整轮构建（源码与旧工程日志确认）

`verify.ts:340` 读取目标文件失败即跳过，不能创建缺失组件。旧宠物预约工程 layout 引用了不存在的 components/layout/site-nav，现有 find/replace 机制无法从无到有补齐它。`verify.ts:437` 仅处理 aborted，不根据 failed/无修改结果调整策略，可能把同一源码反复构建。

建议：修复分为修改现有文件、创建缺失文件、依赖/环境处理；先解析 import 图定位真正缺失项；无源码变更或错误指纹不变时停止重复构建，或切换修复策略。

### 7. 计划降级丢需求，验收只保证技术可运行（源码确认）

`stages/plan.ts:115` 计划校验两次失败后降为仅生成首页，并返回 ok；并未把降级事实作为最终完成门槛。`verification-report.ts:12` 明确 businessVerified=false。当前区分技术检查与业务验收的文案是准确的，但缺少自动验证 SPEC 验收清单的执行器。

建议：失败时重试或明确交付部分结果，不能丢掉页面和接口需求后沿用同一完成状态。为每条核心需求建立需求→文件→API→浏览器操作→证据的对应关系，至少自动检查核心成功流程、错误输入和刷新后持久化。

### 8. 依赖上下文按字符截断，接口契约仍可能丢失（截断机制与长文件确认）

`build.ts:55` 每个依赖只保留前 4000 字符。真实旧预约工程 validation.ts 为 7172 字符，后台 API 为 5225 字符；另一个工程 repository.ts 为 8895 字符。后面的导出、字段或校验规则可能没进入生成上下文。缺失依赖还会被静默跳过。

建议：优先注入共享 DTO、导出签名、请求/响应结构和被引用函数，而非机械取文件前半段；给每个文件展示实际依赖契约，并在生成后立即检查 import/导出闭包。

### 9. 依赖缓存和续聊安装的规则不一致（源码确认）

缓存指纹只看模板 package.json（scaffold.ts:35），恢复检查主要验证 tsc/next 入口。VERIFY 命中后只生成 lockfile，不确保项目新依赖已安装。续聊 install_deps 的描述声称自动选择包管理器，但 tools.ts:213 实际始终 npm install。项目依赖变化后可能得到锁文件、node_modules 和包管理器不一致的状态。

建议：缓存键包括实际依赖清单、锁文件、Node 版本及平台架构；恢复后按实际 lockfile 验证依赖；chat、生成和发布统一工具链。缓存发布采用完整复制完成后原子切换，防止并发读取半成品。

## 第三优先级：视觉与工程治理

### 10. 高质量 UI 目前主要依赖提示词（设计建议）

模板基础 UI 只有 Button/Card/Input，主要通过 SPEC 配色和文字约定控制视觉。尚无固定的页面骨架、设计令牌、组合组件和自动截图验收来保证“一句话生成”的稳定审美。

建议：按展示站、后台工具、表单流程、互动小游戏提供不同骨架；设计令牌与布局由组件实现，AI 聚焦内容和业务；验收覆盖桌面/移动端、加载/空/错误状态与真实按钮行为，避免每次临时创造一套组件接口。

### 11. 生成应用运行环境需要真实隔离（源码确认；开放多人使用前必须处理）

`workspace/command.ts:63` 设置 cwd 后运行 bash，不等于文件系统隔离；命令可以读取绝对路径或父目录。`command.ts:69` 和 `runner.ts:122` 继承平台环境变量，后者仅删除 DATABASE_PATH，平台 OPENAI_API_KEY 仍在继承范围内。未读取或输出任何真实凭据。

建议：使用子进程环境白名单；把生成代码与依赖安装放在隔离运行环境中，限制挂载、资源和访问边界。提示词与危险命令黑名单不能替代运行环境隔离。

## 推荐推进顺序

1. 修复会破坏代码的归一器/输出解析，补充负例测试。
2. 加项目级运行与写入互斥，补全重启后进程管理。
3. 生成阶段超时与心跳；文件级续跑与候选快照。
4. 修复缺失文件和无效重试；统一依赖工具链。
5. 建立需求覆盖与浏览器验收，再完善高质量 UI 骨架。

优先衡量首次生成可运行率、核心流程通过率、续跑保留成功文件的比例、重复错误次数，以及用户等待期间可观察到真实进展的时间。不要只使用 token 数、最终 ready 数或编译成功作为质量指标。
