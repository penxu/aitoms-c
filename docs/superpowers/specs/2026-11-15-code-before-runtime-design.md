# 先生成代码，后准备运行环境

## 目标与范围

用户在线上因 Docker 工具链初始化超时，在准备工程阶段失败，尚未进入需求规格、计划和代码生成。调整生成流程，使代码产出不依赖执行环境；真实安装、构建、服务预览继续经过已有隔离后端。用户已确认实现；本地实现与检查结果见 `docs/code-before-runtime-results-2026-11-15.md`，线上尚未更新。

## 现状依据

- scaffoldProject 在复制模板后调用 ensureGitRepo、commitAll；二者通过 runCommand 触发 ensureWorkspaceRuntime。
- pipeline 在各个非讨论阶段结束后调用 commitAll，即使提交异常仅警告，也会等待初始化，不能只删除准备阶段的一处调用。
- 编写文件阶段通过模型输出、路径校验、语法检查和文件 checkpoint 工作，本身不需要运行生成代码。
- pipeline 在修改之前保护旧预览；实现需核实 pinServiceToSnapshot 的各个分支，保持旧预览可用，避免在无旧预览时提前构建基线。

## 方案比较

1. 推荐：先完成代码生成，把执行环境准备和依赖安装集中到运行验证阶段；运行后端沿用 auto/native/docker，不增加无隔离执行分支。解决代码产出被运行环境阻塞的问题。
2. 仅改为 native：支持 bubblewrap 的主机可以避开 Docker，但仍会让早期阶段依赖运行环境，也不能保证当前服务器支持。
3. 浏览器内预览：适合单独设计纯前端模式，当前 Next.js、SQLite、服务端 API 应用无法直接用静态预览替代。此次不引入第二套应用架构。

## 流程与数据

讨论 → 仅文件操作的准备工程 → 理解需求 → 规划结构 → 逐文件编写与持久化 → 准备隔离环境 → 安装依赖 → 编译和实际运行验证。

前五阶段不执行 shell、不安装依赖、不初始化隔离环境。阶段 Git 提交延后至运行环境可用后；继续使用现有数据库事件、磁盘规格、计划和文件 checkpoint 保留进度。新项目的初始化标识先落盘，保持重复准备的幂等性、目录冲突保护及路径边界。

保留既有预览及其不可变产物。存在旧预览而确实需要迁移或固定产物的情况，必须保留保护行为；无法安全保护时应明确说明原因，不停止已有服务或覆盖正在使用的产物。

运行环境准备在验证阶段执行，展示当前子步骤与受控的进度、错误信息；取消应停止当前任务等待，任何共享初始化进程的终止策略必须避免影响其他等待者。不得把平台凭据或其他工程文件传入生成进程。

## 失败与恢复

运行环境、依赖安装或构建失败时，页面明确区分“代码已生成”和“运行验证失败”，保留源码查看及已有源码导出入口。不显示可用预览，不标记 ready，不将未执行验收当成成功。

允许从验证阶段重试，复用已有规格、计划和文件，不重新讨论、不重新生成代码；刷新或平台重启后仍能恢复这一状态。若已有预览，则继续访问上一次成功版本。

如果目标主机支持 native，可选择现有 native 或 auto 配置以减少 Docker 依赖；如果 native 与 Docker 均不可用，真实预览仍受阻，不静默退化为宿主机裸执行。

## 验收

- 故意令执行后端不可用，准备、规格、计划与代码生成仍能完成；验证阶段给出可恢复错误。
- 测试前五阶段不触发命令、镜像检查、镜像构建或依赖缓存中的运行时探测。
- 恢复运行环境后，仅重试验证即可完成安装、构建与真实预览；已生成文件和确认答案不丢失。
- 验证取消、刷新、重启、已有项目冲突、人工修改保护和旧预览保留。
- 保持既有隔离、项目互斥、实际验收及交付报告语义；运行适用单测、类型检查与 lint。

## 自审

此改动解决生成与运行环境的耦合，不声称能让任意全栈应用在无运行环境时预览。不新增执行后端、不绕过隔离、不把静态展示当作实际应用服务。该范围已由用户确认。
