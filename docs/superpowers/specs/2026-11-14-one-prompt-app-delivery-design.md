# Design — 一句话应用开发与交付

日期：2026-11-14。状态：用户已于 2026-11-14 确认实施。

## Context

动机及范围见 proposal.md，外部行为见四份 delta spec。

当前已存在 Next.js App Router、SQLite、AI SDK、项目文件工具、阶段化生成、NDJSON 事件、开发进程端口池及 ZIP 导出。现有 VERIFY 会执行生产构建，但随后使用现有 runner 启动预览；这不是独立生产发布。当前 ZIP 会包含 `.git` 及大多数项目文件，需要调整交付内容。

现有项目约定要求沿用 Next.js、shadcn/ui、assistant-ui 和 SQLite；本次不更换框架。既有旧规格为扁平 Markdown，当前 CLI 不识别；保留原文，本次新增目录式 delta，归档前明确迁移策略。

## Goals / Non-Goals

目标是完成从输入需求到独立生产版本、可复现部署包的闭环，并在原页面结构内提升完成度。验收失败、模型不可用或无公网条件时，界面准确反映状态。

首版聚焦当前服务器上的单租户可信使用环境。公网多租户执行不可信代码需要容器隔离、身份及权限系统，是另一项上线前置工程；当前方案不宣称具备该能力。第三方云账户连接、自动购买域名、移动端原生安装包、计费和多人协作不在本次范围。部署包指 Web 应用工程及容器配置。

## Decisions

### 1. Approaches

| 路线 | 优点 | 代价及结论 |
|---|---|---|
| 直接把开发服务作为发布 | 改动少 | 后续编辑影响线上，无法固定版本，不采用 |
| 复用生成流水线，新增独立发布模块 | 保留已有能力，发布与预览分离 | 需要快照、生产进程和发布记录；推荐 |
| 全面迁移容器调度和云部署平台 | 隔离和扩展能力强 | 大幅扩张基础设施范围，留作后续 |

推荐第二条路线。用户已授权保留框架并自由设计，具体色彩和模块划分由实现者负责；首版默认部署目标是平台自身服务器。

### 2. 产品流程与界面

保留三层结构：

```text
首页 /        导航 → 一句话输入 → 模板 → 团队/流程 → 案例/FAQ → CTA
项目中心      原侧栏 | 创建输入 + 模板入口 + 真实项目列表
工作台        原侧栏 | 对话/执行记录 | 预览 / 代码 / 交付
                                  顶栏：预览设备、导出、发布
交付面板      当前线上版本 → 发布任务进度 → 版本历史 → 回滚
```

保留营销页现有各区块顺序，包括原有定价区；仅在真实计费未接入时调整文案和入口，不假装能购买。工作台默认显示预览，生成中显示真实进度，用户仍可查看已有文件。移动端用抽屉导航与分页切换，避免强行压缩多栏。

视觉建议：暖白背景、深墨色标题、原品牌蓝 `#4267ff`、少量淡紫辅助色；用大字号和留白突出输入区域。保留 IBM Plex 字体，统一 8px 间距系统、12–20px 圆角、细边框和低强度阴影，图标统一使用现有 lucide-react。动效以 150–240ms 的透明度和位移为主，遵守 prefers-reduced-motion。失败状态保留输入、展示原因和重试，禁止仅记录 console。

### 3. 生成与验收

沿用 scaffold → spec → plan → build → verify，以及现有事件和任务表。SPEC 新增设计约束、核心交互、验收流程及环境依赖，PLAN 保留结构化校验；BUILD 必须复用设计约束而不是逐页随机设计。

未配置模型时在触发前及服务端返回清晰错误。生产构建成功仅说明可构建，不能证明业务完成；为参考预约应用增加端到端核心流程验证（创建预约、持久化、后台查询），并对任意应用输出“已自动检查”与“尚需人工检查”的真实清单，不承诺通用自动证明全部业务。需要外部支付等服务时明确其配置依赖。

不设置产品 token 配额，但模型上下文、供应商限流、命令超时及最多三轮修复仍存在。记录实际用量，用户可取消，禁止无限失败重试。

### 4. 独立发布模块

增加 `app/src/lib/releases/`，按快照、生产进程、状态编排分责。不能将开发 runner 的 stop/restart 语义直接套到生产版本。

建议数据表：

- `releases`：id、projectId、sourceHash、status、createdAt、finishedAt、error、artifactPath。
- `release_events`：发布日志和阶段，供刷新恢复。
- `release_processes`：releaseId、pid、port、status；独立于开发进程记录，但端口分配检查两张表。
- `project_deployments`：projectId 唯一键、activeReleaseId、previousReleaseId、updatedAt。

发布任务按项目加锁，固定源码及依赖锁文件，复制到 `data/releases/{projectId}/{releaseId}`。排除 `.env*`、私钥、`.git`、依赖、缓存、数据库和日志，不跟随符号链接。环境变量由服务器配置注入。生产业务数据库位于 `data/runtime/{projectId}/production`，仅该项目的生产版本共享；开发预览使用独立 development 目录，VERIFY 和端到端测试各使用临时数据库，绝不能写入生产数据。

首次发布默认创建空生产数据库，发布面板明确提示“开发预览中的数据不会自动带到线上”。已有项目工作目录中的 SQLite 数据保持原状，并以兼容路径继续用于开发；首版不自动迁移真实数据到生产。数据导入不在本次交付范围。生成模板通过环境变量读取数据目录，未设置时回退到应用自身的本地数据目录，保持源码包独立运行能力。

流水线：queued → snapshotting → installing → building → starting → checking → published；失败为 failed，平台中断为 interrupted。候选应用使用 `/s/{projectId}` 作为构建时 basePath，生产使用固定 `start` 命令而非 `dev`。代理保留该前缀，与模板 basePath 一致，不能照搬旧设计中剥前缀的描述。

候选应用验证完成后，在事务中更新 activeReleaseId；保留旧版本可回滚。按需重启历史版本，验证健康后切换，之后停止失活进程以释放端口，保留最近五个成功版本的源码与构建产物，活动版本绝不清理。端口池满时发布失败，旧版不受影响。

业务数据不跟随代码回滚；首版要求生成迁移向后兼容。破坏性数据迁移不自动执行，发布前显示阻塞原因，不声称代码回滚能恢复数据库。

### 5. API 与公网

- `GET /api/projects/{id}/releases`：列表、活动版本和发布能力配置。
- `POST /api/projects/{id}/releases`：开始或复用发布任务，返回任务标识。
- `GET /api/projects/{id}/releases/{releaseId}`：状态及有界增量日志。
- `POST /api/projects/{id}/releases/{releaseId}/rollback`：仅允许该项目历史成功版本。
- `/s/{projectId}/**`：生产代理，仅转发到经过验证的活动版本。
- `GET /api/projects/{id}/export?kind=source|deploy&releaseId=...`：区分源码草稿和固定部署包，旧无参数 URL 保持可下载源码。

服务端按项目及 release 归属验证参数，错误响应包含可读信息及合适状态码。前端不得依据 HTTP 200 以外的猜测展示成功。

`PUBLIC_APP_ORIGIN` 是部署环境设置，首版通过 Nginx 同域暴露 `/s/`，不接受用户输入任意探测地址。未配置则仅显示本地发布状态。部署验收必须从服务器之外访问公开地址并检查页面、资源、API，不以生成一个 URL 作为上线证据。

### 6. 部署包

新增 package 模块，采用允许的源码目录和文件白名单、严格秘密排除及不跟随链接的遍历。保留锁文件与 `.atoms` 内需求/计划，排除 `.git` 以及运行数据。与旧文档“导出含 git 历史”存在行为差异：本次默认导出改为可安全交付源码，README 和旧导出说明需同步标明；保留服务器内 git 历史用于追溯。

部署包提供 Dockerfile、Compose、`.dockerignore`、已清理的 `.env.example`、README 和包含 sourceHash、运行时要求、构建验证状态的 manifest。Docker 基础运行时需兼容 SQLite 原生依赖；提供持久卷及生产健康检查。Dockerfile 明确执行 build/start，默认根路径，与平台 `/s/` 构建不同，需要在根路径环境重新验证；不把带平台 basePath 的构建缓存打入包。

打包前选择固定快照，完成归档到临时文件并验证可读取后才返回下载，取消下载清理临时文件。未验证源码包标为草稿，部署包与验证记录按源码哈希绑定。

### 7. 文件边界

修改 marketing-page、dashboard-page、workspace 及样式；将发布面板抽到独立组件。生成规则改动集中在 prompts 和 spec schema。发布、打包和生产代理独立模块，复用已有路径校验及数据库连接，不重复实现文件权限层。改动 Next 路由前阅读本地 Next.js 文档。

## Risks / Trade-offs

- 单机运行生成代码的隔离不足 → 首版限定可信单租户；公网多租户之前补独立沙箱和认证。
- 构建资源占用影响现有进程 → 全局限制重型构建并发，等待队列及占用状态可见。
- 本地与公开访问不同 → 本地功能验收与服务器外公网验收分开记录。
- 快照时源码变化 → 生成、修改与快照使用项目级互斥，固定哈希后才构建。
- 停机与重启 → 启动时恢复活动生产版本、核对进程及探活，未完成任务标中断；首版不承诺跨机器高可用。

## Migration Plan

1. 先增加幂等数据表和配置，不改变现有项目或预览入口。
2. 完成状态机、快照、生产构建与代理，再开放发布按钮。
3. 更新打包规则和 README；已有磁盘工程及 git 历史保留。
4. 完成视觉升级并执行回归；发布失败不得改变原活动版本。
5. 代码回退时保留新表和产物；移除新入口前记录活动线上版本并制定停服窗口，不静默删除发布数据。

## Verification

核心自动验证覆盖：同项目重复发布、失败不切换、回滚归属、重启中断、快照排除、哈希一致、归档有效、代理资源及 API 路径。浏览器验证覆盖输入到预览、预约提交持久化、发布后修改隔离、回滚和干净环境部署包。视觉检查覆盖 375/768/1440px、键盘导航、错误及空状态和减少动效。

发布公网验收依赖实际服务器环境。未提供该环境时可完成本地实现和部署产物，必须准确报告公网尚未验证。
